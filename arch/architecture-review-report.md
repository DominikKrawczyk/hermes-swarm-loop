The code is functional (390/390 tests pass), but the architecture docs are stale and must be updated to match the actual v6.5.1 implementation.

The CAS version guard fix (Bug C1-C3, critical), the MasteryGate dimension check fix (Bug C4, critical), and the CircuitBreaker auto-recovery fix (Bug H2-H3, high) are architectural-level fixes that the architecture docs do NOT reflect.

## 1. HIGH: File Structure — Architecture Doc vs Reality

### Issue: Architecture doc describes separate files; code uses single file

**Arch doc** (architecture-overview.md, file layout and state-machine-architecture.md):
```
engine/
├── state_db.py          # SQLite backing store
├── phase_machine.py     # Phase lifecycle
├── point_machine.py     # Point lifecycle
├── yolo_machine.py      # YOLO zone management
├── mastery_gate.py      # 7-dim scoring & verdict
├── gate_verifier.py     # Handoff validation
└── gate_11.py           # 11-agent gate verifier
```

**Actual code** (single file, 535 lines):
```
engine/
├── state_machine.py     # StateDB + PhaseMachine + PointMachine + YOLOMachine (ALL in one file)
├── mastery_gate.py      # ScoreCard + MasteryGate
├── gate_11.py
├── gate_verifier.py     # (dead code — deleted, then recreated by agents)
└── workspace_manager.py
```

**Impact:** HIGH for anyone reading the architecture docs to understand the codebase — the docs describe a modular architecture with 4 separate state machine files, but the actual code is a monolith. This makes the file layout section misleading.

**Recommendation:** Update architecture-overview.md and state-machine-architecture.md to document the actual state_machine.py monolith, OR refactor code to match the documented architecture.

## 3. HIGH: CASStore Implementation is Completely Different

### Issue: Architecture doc describes SQLite-backed store; code is pure in-memory dict

**Arch doc** (scaling-infrastructure.md):
- CASStore uses SQLite with WAL mode, retry_on_conflict=3, lock_timeout_ms=5000
- API: get(), set(), cas(), update(key, transform), delete()

**Actual code** (scaling/cas_store.py):
- Pure in-memory dict-backed store with threading.RLock
- No SQLite, no WAL, no retry logic
- API: set(), get(), cas() (value-based, not version-based), delete(), exists(), keys(), size(), clear()
- update(key, transform) — does NOT exist
- CasEntry class and ConflictError are dead code (not used by runtime)

**Impact:** HIGH. Anyone implementing distributed coordination based on the architecture doc would design around SQLite-based CAS with retry logic, but the actual store is ephemeral in-memory. The API surface is also different (no `update` method, no retry).

**Recommendation:** Either update the scaling doc to describe the in-memory store accurately, or implement the SQLite-backed CASStore that the architecture describes. The current in-memory store cannot survive process restart.

## Design Debt

### D1: State Machine Monolith vs Documented Modular Design

The architecture docs describe a clean modular design with separate files for each state machine. The actual code puts everything into a single state_machine.py (535 lines, 12 public methods + internal helpers). This makes the code harder to maintain — any single change requires understanding the entire file.

**Severity:** MEDIUM
**Effort to fix:** LOW — split into state_db.py, phase_machine.py, point_machine.py, yolo_machine.py with state_machine.py as a re-export module or compatibility layer.

### D2: CASStore Implementation is In-Memory — No Persistence

The architecture doc describes a SQLite-backed CASStore with retry logic and WAL mode, but the actual implementation is in-memory dict. This means:
- All CAS state is lost on process restart
- No concurrent process safety (only thread-safe, not process-safe)
- The ConflictError class is dead code (never raised by cas_store.py)

**Severity:** MEDIUM-HIGH (depends on whether CAS state needs to survive restart)
**Effort to fix:** MEDIUM — implement SQLite-backed CASStore matching the architecture spec.

## Missing Abstractions

### M1: No Formal Phase↔Point Dependency Tracking

The state machine manages phases and points independently, but there is no formal dependency tracking between points within a phase. The PhaseMachine tracks `completed_points` as a counter, not as specific point completion status. This means:
- An ARCH agent cannot programmatically discover which SETUP points must complete first
- The point→phase dependency is implicit (settled by correct sequencing in bootstrap)
- No graph-based dependency resolution

**Severity:** LOW (the bootstrap sequence is deterministic, so this isn't causing bugs)
**Recommendation:** Add optional dependency graph in point_state with `depends_on` column.

## Over-Engineering Assessment

### O1: 7 Scaling Modules — Only CASStore and ConnectionPool Have Active Consumers

The scaling layer contains 7 modules: TokenBucket, AdaptiveBatcher, CASStore, CircuitBreaker, ConnectionPool, PriorityQueue, and QueuePressure.

Of these, only **CASStore** (used by state machine for thread-safe state) and **ConnectionPool** (used by the CLI for DB connections) have active runtime consumers. The remaining 5 modules (TokenBucket, AdaptiveBatcher, CircuitBreaker, PriorityQueue, QueuePressure) are fully implemented and tested but **not wired into any runtime code path**.

This was by design ("future-ready infra" per the review report), but ~500 lines of well-tested code have no active callers.

**Severity:** LOW (infrastructure ready, no harm — just note for clarity)
**Recommendation:** If these scaling modules remain unwired through Phase 3, consider a Simplicity phase to remove or consolidate them.

## Incorrect Assumptions in Architecture Docs

### A1: Arch doc assumes 5-phase cycle; actual cycle uses 3-phase swap

The architecture-overview.md shows a linear 5-phase pipeline with a simplicity loop. The actual execution model uses Phase 1 exactly once, then alternates Phase 2↔Phase 3 until the Mastery Gate passes. Simplicity is an optional separate pass, not part of the main cycle.

### A2: Arch doc assumes MasteryGate runs per-point; actual runs at end of Phase 3

The state-machine-architecture.md implies gate checks after each point, but the skill says the Mastery Gate runs at the end of Phase 3 only (or at CROSS-CHECK resolution).

### A3: Arch doc assumes `admit()` returns bool with safety valve check ✓

The yolo-zones.md describes `admit()` as checking safety valve + max_parallel. This matches the code.

## Conclusion
